# 自动维护中心 v3 — 设计文档（收窄版：本体更新监控）

日期：2026-11-23
状态：待用户批准
上游：v1（全自动入库）、v2（入库中心，已交付）。本文设计 v3，不覆盖 v1 运行副本；接入 v2 的方式见 §6.4，须用户确认后才动。

## 1. 意图与 why（收窄后）

用户原问："steam 更新检测+自动适配加密游戏的 lua/补丁抓取能否夜间自动化"。经 recon 与场景走查，需求已两次收窄，最终只剩一个真问题：

> **破解游戏（如剑星 v1.4.1）的游戏本体一旦被 Steam 自动更新，打进去的 Voices38 补丁就失效。** 这才是需要解决的。

非加密游戏本体更新无害（见 N2），不需要监控。OST 注入层由 OST 自己恢复（见 N3），也不需要守护。因此 v3 收敛为**一件事**：入库中心启动时，检查已锁定的破解游戏本体有没有被更新，变了就告警并给出重锁入口。

## 2. 目标

- **G1 基线**：为每个"已验证破解 + 已锁定 GID"的游戏，记录一份本体版本基线（buildid + 已装 depot 的 manifest GID）。
- **G2 检测**：入库中心启动时后台比对当前 `appmanifest_*.acf` 与基线，发现版本变化即判定"补丁可能失效"。
- **G3 告警与出口**：只报不改——告警文案给出"去版本锁定 tab 重新锁定并重打补丁"的操作入口，不自动下载、不自动重锁。

## 3. 非目标 / 反目标（本次明确不做）

- **N1 不做独立守护 exe / 计划任务 / 开机自启**。用户已否决（"自启动影响体验"）。零常驻、零系统改动。
- **N2 不监控非加密游戏本体更新**。无 Denuvo 类版本绑定补丁，更新后照玩。两个例外与加密无关：①游戏目录里的联机 mod（BepInEx）可能被覆盖需重装；②锁了 GID 的游戏会停在旧版（旧版照样能玩，不算坏）。
- **N3 不管 Steam 客户端更新 / OST 注入层**。实测 OST 每次启动 Steam 会按当前 DLL 哈希自行拉 pattern/ipc（缓存 mtime 跟随 Steam 启动时间），上游有就自恢复；本机无编译器/逆向能力，拉不到只能等上游，守护重复拉同 URL 是冗余。三件套 DLL 的误删补回线一并砍掉。
- **N4 不自动下载/导入补丁**。网盘无 API、版本一一对应，必须人工下载确认。
- **N5 不自动刷 GID**。实时 GID 会冲掉锁定版；已锁定游戏永不自动刷新 GID（铁律）。
- **N6 不改"来自家庭库"显示**。Steam 服务端账本判定，本地改不了。

## 4. 约束

- **C1** 新目录 `D:\STEAM入库\全自动入库_v3\` 放模块与文档；v1（`D:\STEAM入库\全自动入库`）运行副本只读不改。
- **C2** 零硬编码路径，复用 v2 `paths.py`（注册表/进程/常见目录探测）。
- **C3** Python 3.14 + tkinter，PyInstaller onefile；数据文件外置根目录可独立更新。
- **C4** 接入 v2 需先备份 `src\main_app.py` 与 `入库中心.exe`，改完可一键回退；这是唯一会触碰已交付产物的动作，须用户点头（见 §9）。
- **C5** 检测全程只读 `appmanifest_*.acf` 与本地 JSON，不写游戏文件、不碰 Steam 运行状态。

## 5. 方案

选：**启动自检**——把检测塞进入库中心.exe 的启动流程，用户打开工具时后台跑一次。

### 否决理由
| 备选 | 否决理由 |
|---|---|
| 独立守护 exe + 计划任务 | 用户明确否决自启动；且与"每次入库都会打开工具"的实际习惯重复 |
| 夜间定时任务 | 本体更新随时可能发生，夜间才查反而滞后；且需改系统状态 |
| 监控客户端更新/注入层 | OST 自恢复，重复劳动；本机无逆向能力兜底 |
| 监控全部游戏 | 非加密游戏更新无害，纯噪音 |

## 6. 设计

### 6.1 技术依据（2026-11-23 实测）

`F:\SteamLibrary\steamapps\appmanifest_3489700.acf` 关键字段：
- `buildid = 26123051`、`TargetBuildID = 26123051` —— 本体版本标识。`TargetBuildID != buildid` 表示有更新待应用。
- `InstalledDepots` 内 `3489701/3596180/3596190` 的 `manifest` = `2747626496734343426 / 8344797041293440177 / 6588499701851943951` —— 与 `crack_library.json` 里剑星的 `locked_gids` 完全一致。
- `AutoUpdateBehavior = 1` —— 记录字段，确切语义未核实，**不作为判据**。

判据只用 `buildid` / `TargetBuildID` / 已装 depot 的 manifest GID 三者，均为 Steam 明确语义。

### 6.2 基线与检测对象

- **检测对象**：`crack_library.json` 里 `verified = true` 且带 `locked_gids` 的游戏（当前只有剑星 3489700）。非此集合一律跳过。
- **baseline.json**：`{appid: {name, buildid, target_buildid, manifest_gids:{depotid:gid}, captured_at}}`，首次启动时从当前健康 acf 建立（此时是刚打好补丁的状态，属可信基线）。
- **比对规则**（任一命中即判"本体变更"）：
  1. 当前 `buildid` 与基线不同；
  2. 当前 `TargetBuildID != buildid`（有更新挂着没应用）；
  3. 已装 depot 的 manifest GID 与基线任一不符（本体文件被换）。
- **无基线**（首次）→ 建立基线，不告警。
- **acf 不存在**（游戏未安装）→ 跳过，不告警。

### 6.3 模块 `update_guard.py`（v3 产出）

复用 v2 模块（复制进 v3 源码目录，**不 import v2**，避免写回 v2）：`paths.py`、`backup.py` 仅用其 `writable_dir()`；crack_library 数据读 v3 根目录副本。

接口：
- `BASELINE_PATH = writable_dir() / "baseline.json"`
- `read_acf(appid) -> dict | None`：遍历各 Steam 库目录找 `appmanifest_{appid}.acf`，正则提取 buildid/TargetBuildID/InstalledDepots 的 manifest GID；找不到返回 None。
- `locked_apps() -> dict`：读 `crack_library.json`，筛 `verified and locked_gids`。
- `build_baseline(force=False) -> dict`：对每个 locked app 读 acf 写基线；已有且不 force 则跳过。原子写（os.replace）。
- `check_updates() -> list[dict]`：返回变化项 `[{appid, name, reasons:[...], current, baseline, advice}]`，只读不写。
- `format_report(items) -> str`：中文告警文案 + 操作入口。

### 6.4 接入 v2（须确认，见 §9）

- 把 `update_guard.py` + 一份 `crack_library.json` 复制进 `D:\STEAM入库\全自动入库_v2\src\`（数据文件外置 v2 根目录可更新）。
- 改 `v2\src\main_app.py` 的 `App.__init__`：起一个 daemon 线程 → 无基线先 `build_baseline()`，再 `check_updates()` → `after()` 回主线程；仅在有变化时在"版本锁定"tab 顶部状态标签显示告警，并弹一次非阻塞提示。不新增 tab。
- 备份原 `main_app.py` 与 `入库中心.exe` 到 `v3\integration_backup\`，重打包后验收；用户可一键回退。**v1 全程不碰。**

### 6.5 告警示例

```
⚠ 剑星（3489700）本体版本已变化，Voices38 补丁可能失效

   处理：到「版本锁定」tab 重新应用锁定 GID → 重下锁定版 → 重打补丁
```

## 7. 自由项（我做的主，用户可改）

- 基线首次建立不告警（假设当前状态可信）。
- 告警只弹一次（同一次启动内），不刷屏。
- 不新增 tab，塞进现有"版本锁定"tab 顶部状态行。
- 数据文件外置 v2/v3 根目录，可独立更新。

## 8. 验收标准

1. `pytest` 全绿；`py_compile` 通过。
2. `read_acf(3489700)` 真机返回 buildid=26123051、3 个 manifest GID 正确。
3. `build_baseline()` 生成 baseline.json；无变化时 `check_updates()==[]`。
4. mock 改动 buildid / TargetBuildID / 某 depot GID 三种情况，各自能被判出并给正确告警文案。
5. 非锁定游戏（如 550）不进检测集合。
6. 接入后入库中心.exe 冒烟：4 tab 正常、启动自检后台跑完不卡 UI、无变化不弹窗。
7. v1 运行副本哈希与 v2 验收基线不变；v2 改动可凭 `integration_backup\` 一键回退。
